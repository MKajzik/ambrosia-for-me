# Backend (Go)

Module: `github.com/InzKazik/mealplanner/backend`. Go 1.26, `chi` router, `pgx` + `goose` + `sqlc` for Postgres.

## Layout

- `cmd/api/`: process entry. Load config, connect Postgres, wire services, serve HTTP, graceful shutdown on SIGINT/SIGTERM. No business logic.
- `cmd/migrate/`: apply pending migrations, exit. API never applies migrations.
- `internal/config/`: env config + validation.
- `internal/api/`: **generated** from `openapi.yaml` (`api.gen.go`, never hand-edit) plus `oapi-codegen` config (`oapi.yaml`). Generated file embeds spec (`api.GetSpec()`), used by request validator.
- `internal/httpapi/`: HTTP layer. Router, middleware (request ID, client IP, logging, panic recovery, CORS, body limit, rate limits), OpenAPI request validator (also authenticates), problem+json writer, handlers implementing `api.ServerInterface` (`account.go`, `server.go`). Calls services only.
- `internal/auth/`: password hashing (argon2id), access/refresh tokens. Pure: no DB, no HTTP.
- `internal/service/`: business rules. `Auth` = registration, login, refresh-token sessions, signed-in user's account. `Partners` = the invite-code link between two users. `Meals`, `DietTemplates` and `ShoppingLists` apply the partner visibility rules (see below). Never speaks HTTP.
- `internal/usda/`: FoodData Central client + category/nutrient mapping tables, used only by `cmd/import-usda`. Talks to `store` directly, not via `internal/service`.
- `internal/store/`: **all SQL**. `queries/*.sql` = source; `sqlc/` generated from it + migrations (never hand-edit). `Store` adds transactions.
- `internal/db/`: pgx pool + goose migration runner.
- `internal/testutil/`: integration-test helpers (Postgres via testcontainers; migrated template DB copied per test).
- `migrations/`: embedded goose SQL migrations.

Deps point one way: `httpapi` → `service` → `store`; `auth` = leaf used by `service` and `config`. Package never imports one to its left. `internal/usda` = separate leaf-like package beside `httpapi`, not below `service`: imports `service` directly (nutrient-key constants only) and `store` directly, so `service` must never import `usda`. One documented exception inside `service`: `Plan` depends on `Meals` (see doc comment on `Plan` type in `plan.go`), to reuse `Meals.Get` nutrition computation instead of third copy of unit-conversion/null-propagation logic.

## Commands (from repo root)

- `make test-backend`: `go vet ./...` and `go test ./...`. **Needs Docker** (integration tests start Postgres via testcontainers). No Docker → skip locally, fail when `CI` set, so CI can't pass silently without them.
- `make lint-backend`: golangci-lint v2.13.2 via `go run` (same as CI), incl. `gofmt`, `gosec`, `bodyclose`, `sqlclosecheck`.
- `make generate`: regenerate `internal/api/api.gen.go` (oapi-codegen) and `internal/store/sqlc/` (sqlc)
- `make check-generated`: fail if committed generated code differs from spec, migrations, queries, or generated file not committed
- `make migrate`: apply migrations to `DATABASE_URL` (default compose DB)
- `make run-api`: run on `API_ADDR` from process env (default `:8080`; `.env` not loaded). Needs `make db-up` + `make migrate` first. Defaults `JWT_SECRET` to public dev-only secret and sets `ALLOW_DEV_JWT_SECRET=1`, which API requires before accepting that secret; every other env must set own `JWT_SECRET`.

## Conventions

- **Routes:** edit `openapi.yaml` first, run `make generate`, implement new `api.ServerInterface` method. Build fails until done. Handlers non-strict (`w, r`); contract tests + request validator catch drift instead of typed responses.
- **Auth is decided by the spec.** Global `security: bearerAuth` protects every op; `security: []` opts out (only health checks and `auth/*`). Validator in `internal/httpapi/auth.go` enforces it, puts user in request context (`httpapi.UserID(ctx)`), so route added to spec protected by default. Never add path-based auth checks.
- **Requests are validated by the schema** (shape, lengths, formats, unknown fields), reported as `400 validation_failed` with per-field `errors`. Service code enforces business rules only.
- **Contract tests:** every new endpoint gets test via `contract(...)` in `internal/httpapi/contract_test.go`, validating request + response against `openapi.yaml` (`withInvalidRequest()` for deliberately bad requests). Error responses use shared `components/responses` (`BadRequest`, `Unauthorized`, `Conflict`, `TooManyRequests`).
- **Errors** use `httpapi.WriteProblem` / `WriteValidationProblem` (RFC 9457 `application/problem+json`) with stable `code` constant. Add new codes to `problem.go`, document in spec.
- **SQL** only in `internal/store/queries/*.sql`; run `make generate`, commit output. Services take `*store.Store`, use `InTx` for multi-statement changes, translate DB errors to service errors (`store.IsUniqueViolation`, `store.IsNotFound`).
- **Secrets never reach logs or errors**: no passwords, tokens, refresh tokens, JWT secret, query strings. Compare secrets constant-time (argon2id + JWT libs do).
- Every response carries `X-Request-Id`. Log with `slog` (JSON to stdout), include `httpapi.RequestID(ctx)`. No `fmt.Println` in non-test code.
- **Migrations** = goose SQL files `NNNNN_description.sql` in `migrations/`, forward-only in prod. Every table has `created_at`, `updated_at`, and `updated_at` trigger using `set_updated_at()`, except line-item tables fully owned by parent row and always replaced wholesale, never edited in place (`meal_ingredients`, `template_slots`): neither column.
- **Tests** table-driven when several cases. Handler tests use `httptest`; integration tests use real Postgres via `testutil.NewMigratedDatabase` (or `NewDatabase` for empty), never mocks. Light argon2 params in tests (`auth.HashParams{MemoryKiB: 8, Iterations: 1, Parallelism: 1}`).
- Config from env vars, documented in `.env.example`.

## Behaviour worth knowing

- Refresh tokens rotate every use. Presenting already-used or revoked token revokes whole session family, so client retrying refresh after network failure gets signed out: clients must serialize refreshes, keep only newest token.
- Login answers unknown email and wrong password identically, same hashing time. Registering existing email → `409 email_taken`, which does reveal email exists.
- Access tokens stateless, live 15 min; deleted account's token rejected only because `/me` looks user up (401 `unauthorized`).
- Logout revokes refresh tokens only: issued access token keeps working until expiry (max 15 min).
- Every table hanging off user must use `ON DELETE CASCADE`, else account deletion leaves orphans, breaks in-app deletion guarantee (`refresh_tokens` does).
- **Cascades alone are not enough for account deletion.** `users` cascades to `ingredients`, `meals`, `diet_templates`, `plan_entries`, `shopping_lists`, `partnerships`, but `meal_ingredients.ingredient_id` and `template_slots`/`plan_entries.meal_id` deliberately `NO ACTION` (makes deleting in-use ingredient/meal a `409`), and Postgres fires table's own cascade trigger in order codebase doesn't control. `Auth.DeleteUser` deletes explicitly, one transaction, in only working order: lock the user's `users` row (`FOR NO KEY UPDATE`, as `Partners.Invite`/`Accept` do), then `partnerships` (so it waits for a partner's in-flight shopping-item edit, which holds the partnership row `FOR SHARE`, before any list or item lock is taken; one lock order everywhere: users, partnership, list, item) → `shopping_lists` (cascades `shopping_items`; first only to keep chain explicit, since `shopping_items` refs to `ingredients` and `users` are `ON DELETE SET NULL`, can't abort anything) → `plan_entries` → `diet_templates` (cascades `template_slots`) → `meals` (cascades `meal_ingredients`) → `users` (cascades `ingredients`, now safe since nothing in `meal_ingredients` still refs them). Any future table that both cascades from `users` and is referenced `NO ACTION` from another user-owned table needs same treatment, in right position in chain. `partnerships` is not order-sensitive for the `NO ACTION` chain (nothing references it `NO ACTION`, and its user columns still cascade as the safety net); it goes first only for the lock order above, and deleting it ends the partner's access at once.
- Rate limits (10 auth req/min per client IP, 300 req/min per user, and 10 `POST /partner/accept` per hour per user and, separately, per client IP) in memory: with several replicas, effective limit per replica. The accept limit (`RateLimits.AcceptPerHour`) is tight because an invite code has only about 39 bits. `TRUSTED_PROXY_COUNT` must match real proxy count, or clients forge IP.
- **Rate-limit gaps (accepted for now).** Validator-rejected requests (401 or 400) don't count toward per-user limit; no per-account failed-login throttle, so credential stuffing across many IPs limited only by argon2id cost; shared NAT egress IP shares one 10/min auth bucket; unauthenticated traffic to non-`auth/*` routes and health checks unlimited at app layer. Put edge proxy or global per-IP limit in front before exposing API. Planned hardening: per-account counter with backoff + shared counter store.
- **Proxies.** `TRUSTED_PROXY_COUNT` must equal real proxy count in front of API: too high → clients forge IP, too low → everyone shares proxy's bucket. Bind API only to proxy network. Proxy putting ports in `X-Forwarded-For` makes every client share one bucket.
- **Personal data in logs.** Request log records `remote_ip`. Decide + document retention period before prod.
- **Header and body edge cases.** Request with >1 `Authorization` header rejected (401). Body over 64 KiB → `400 request body is too large` on unauthenticated routes; on secured routes currently reads as `401`, because kin-openapi wraps read error in security error.
- **Ingredient search is not paginated.** `GET /ingredients?q=` ranks by trigram similarity, returns up to `limit` results, no cursor; only plain alphabetical listing (no `q`) paginates. Type-ahead UI never needs second page, and similarity-ranked set has no stable order to cursor over.
- **Nutrients use two schemas on purpose.** `NutrientAmounts` (`Ingredient` response) requires all 18 keys, always present, `null` where unknown. `NutrientAmountsInput` (`CreateIngredientRequest`/`UpdateIngredientRequest`) requires none, so client sends only known nutrients. Reusing `NutrientAmounts` for requests tried first, rejected: validator rejected any partial nutrient object, defeating optional input. On update, supplying `nutrients` field at all replaces entire nutrient set (any of 18 keys not included cleared, not kept); only omitting `nutrients` entirely leaves existing unchanged.
- **Meal nutrition is per serving, and a missing nutrient propagates, not zeros out.** `Meal.NutritionPerServing` = sum of every ingredient line's contribution / `servings`; multiply by `servings` client-side for meal total. Nutrient key `null` in response if *any* ingredient lacks value for it — treating unknown as zero would understate total, which meal-planning app can't do quietly. Meal with zero ingredients reports `0` for every key (well-defined empty sum, different from "unknown").
- **Clearing an ingredient's conversion factor while a meal depends on it is rejected at write time.** `Ingredients.Update` checks before writing whether clearing `grams_per_piece` or `density_g_per_ml` would strand a `meal_ingredients` row using this ingredient with `piece` or `ml` unit (`IngredientHasUnconvertibleMealUsage`, scoped to caller's own ingredients so never leaks another user's meal usage). If so → `409 unit_not_convertible` (`ErrIngredientInUseByUnconvertibleUnit`), nothing written — meal, and any plan day or template scheduling it, unchanged. Mirrors deleting in-use ingredient, blocked same way (`409 ingredient_in_use`, via `meal_ingredients_ingredient_id_fkey` FK). `ErrUnitNotConvertible` (read-time check in `toMeal`/`gramsFor`, which `GET /plan` also runs via `Plan.GetRange` → `Meals.Get` for every scheduled meal in range) now unreachable through normal sequential use — every write path that could produce unconvertible row validated first — kept only as defensive fallback for narrow accepted race: `Ingredients.Update` check and concurrent `Meals.ReplaceIngredients` read of same ingredient run in separate transactions with no cross-table lock, so adversarial timing can still interleave badly.
- **`plan_entries` and `template_slots` allow multiple `snack` rows per day; the other three slots don't.** `PUT/DELETE /plan/{date}/{slot}` addresses slot only by enum value, so `snack` can't be true upsert like `breakfast`/`lunch`/`dinner`: `PUT .../snack` always adds new entry, `DELETE .../snack` removes every snack entry for date. Manual `PUT` (any slot) always clears `from_template_id` to `null`, even when overwriting entry from applied template.
- **`diet_templates.day_count` is immutable after creation.** No PATCH field; recreate or `POST /diet-templates/{id}/copy` to change. `PUT /diet-templates/{id}/slots` validates every slot's `day_index` against existing `day_count` at write time — no DB constraint (`CHECK` can't compare against another table's column).
- **Deleting a meal fails with `409 meal_in_use` if a diet template's slot or a plan entry still references it**, same `NO ACTION` FK pattern as `ingredient_in_use`. `Auth.DeleteUser` deletes `plan_entries`, then `diet_templates` (cascades `template_slots`), then `meals`, then user row, in that order, one transaction — see cascades note above.
- **A shopping item is a snapshot, so it never blocks deleting its ingredient.** `shopping_items` stores own `name`, `quantity`, `unit`, `category`; `ingredient_id` is `ON DELETE SET NULL` (not `NO ACTION` like `meal_ingredients`), so deleting custom ingredient turns referencing items into free-text items. `origin` unchanged, so `generated` one still replaced on next regeneration.
- **Shopping item edits are versioned; checks are not.** Every change bumps `version`; `PATCH` response carries new one. Changing `name`/`quantity`/`unit`/`category` needs current `version` (`400 version_required` without, `409 version_conflict` with current item in problem's `current` member when stale). `checked`-only `PATCH` = last-write-wins, ignores `version`; setting `checked` to current value = no-op (no bump, no event), which makes offline replays safe. Item `DELETE` unversioned. `UpdateItem` locks item row (`SELECT ... FOR UPDATE`) before version check; regenerating and adding items lock list row (`SetShoppingListSourceForUser`, `TouchShoppingListForUser`), same concurrent-replace fix as `TouchMealForUser`.
- **Generating a list merges per ingredient, preferring the unit the recipes used.** Each meal line counts `quantity × portion / servings`. Ingredient used in one unit throughout keeps it ("6 piece"); mixed units merge into grams via `gramsFor` (meals conversion); unconvertible unit keeps own line. `POST /shopping-lists/generate` with `list_id` regenerates that list: `generated` items replaced (come back unchecked), `manual` items untouched.
- **Shopping-list events are in memory, per process.** `ListEventHub` fans each committed change to open `GET /shopping-lists/{id}/events` streams of this process only: with several replicas, client sees only events from its connected replica, converges by refetching on reconnect and foreground (spec §4.3). Subscriber >32 events behind disconnected rather than silently missing events (versions per item, so dropped event not reliably detectable as gap). Stream clears server `WriteTimeout` for own response, and `serve` closes hub from `RegisterOnShutdown`, so shutdown ends streams without cancelling ordinary requests. Token only in `Authorization` header, so web client must use fetch-based SSE reader, not `EventSource`.
- **Partner link (`Partners`).** `POST partner/invite` creates a `pending` `partnerships` row holding only the SHA-256 of an 8-character code (alphabet `23456789ABCDEFGHJKMNPQRSTUVWXYZ`), valid 48 h; a new invite replaces the caller's old one. `POST partner/accept` activates it and clears code and expiry, so a spent code cannot replay. Wrong, expired, own and used codes all answer `404 invite_invalid`. A caller who is already linked gets `409 partner_already_linked` before any code lookup, so `accept` is no oracle for guessing codes. `Invite` and `Accept` lock the involved `users` rows (`FOR NO KEY UPDATE`, in id order) and check again, because "a user appears once across both columns of active rows" cannot be an index; `Accept` also drops the caller's own pending invite. `DELETE partner` (either side) hard-deletes the row; re-linking is a fresh invite. `GET partner` reads an expired pending invite as `404 partner_not_linked`.
- **Partner visibility is one read predicate.** `owner_id = @user_id OR (owner_id = @partner_id AND shared_with_partner)`, with `partner_id` NULL when the caller has no partner. `activePartnerID`/`partnerOrNil` (package functions in `service/partners.go`) resolve the partner once per transaction, uncached, so an unlink shows in the next transaction. Only `Get` of a meal, template or list, `Copy`, and shopping-item writes and `Subscribe` use it. `List` stays owner-only, and `GET partner/{meals,diet-templates,shopping-lists}` list only what the partner shared (`shared_only` in the list queries). Every other write, `DietTemplates.Apply` and the plan stay owner-only (`Plan` reads meals through `Meals.GetOwn`, and `SetEntry` calls `GetMealForUser` without a partner), so a partner gets `404`. Meals, templates and lists carry `is_owner`.
- **Sharing a template shares what its slots show.** A partner reading a shared template sees each slot's `meal_id` and meal name even when the meal is not shared; `GET /meals/{id}` on it stays `404`. Copy reads the meals through the template.
- **Copying a partner's meal or template duplicates what it needs.** `ingredientCopier` (`service/copy.go`) duplicates each distinct custom ingredient, with its nutrient rows, into the caller's library once per copy operation and keeps global (USDA) ingredients as shared references. A partner template copy also copies each distinct meal once, private. An own copy is unchanged (same meals, same ingredients). Copying twice duplicates twice; there is no dedupe across copies. Copies never change with the original.
- **Shared shopping lists.** The partner may add, edit, check and delete items and open the event stream; rename, delete, toggling `shared_with_partner` and regenerate are owner-only (`404` for the partner), and regenerate reads the owner's `plan_entries`. `checked_by` is the acting user (cleared on uncheck, `ON DELETE SET NULL`). Partner-added items are `manual`, so the owner's regenerate keeps them. Item writes take the partnership row `FOR SHARE`, so an unlink waits for edits in flight and any edit after it finds no partner.
- **Unlink, unshare and account deletion close event streams.** `ListEventHub` subscriptions record watcher and list owner. `Partners.Unlink` calls `CloseAccess`, turning sharing off calls `CloseListForNonOwners`, and `Auth.OnUserDeleted(listEvents.CloseUser)` (wired in `cmd/api`) closes every stream touching a deleted account, whose lists are removed by a raw `DELETE` that publishes nothing. `Subscribe` registers with the hub first and then re-checks access under `FOR SHARE`, so an unlink cannot slip between them. Like the rest of the hub this is per process.

## Decide before the domain plans

- ~~**Access tokens versus deleted or logged-out users.**~~ Resolved for ingredients: `Ingredients.Create` translates `ingredients_owner_id_fkey` FK violation into `service.ErrNotFound`, mapped to `401` exactly like `GetUser`. Every future user-owned write table should follow same pattern (named FK constraint + `store.IsForeignKeyViolation` check), not the also-considered validator-level fix.
- **`DELETE /me` needs no re-authentication.** Stolen 15-min access token irreversibly deletes account and, later, everything it owns. Changing after web + iOS clients exist = breaking contract change: decide whether request must carry password or fresh refresh token.
- **Registration reveals whether an email exists** (`409 email_taken`) while login equalised. Accept + record in privacy notes, or move to always-`201` flow with email verification once email exists.
- **argon2id memory is not bounded by concurrency.** Each in-flight hash holds 64 MiB; only brake is per-IP limit, counted per replica. Add bounded semaphore (~`GOMAXPROCS`) answering 503 when full, before public exposure.
